# Privacy Protocol Selection

## Decision Record

**Status: NO-GO. No production ballot protocol is selected or integrated.** The repository cannot currently implement the requested combination of anonymous eligibility, public-chain replay prevention, secret ballots, proof-checked valid ballots, independently verifiable tally, and no single-party decryption authority without introducing an unverified cryptographic construction or a large, unaudited protocol bridge.

**Answer to the required question: Can this repository implement the required privacy properties without introducing an unverified cryptographic construction? No, not with the maintained integrations and deployment artifacts currently available in this project.** The frontend remains fail-closed for voting. The old Solidity contract remains a public-vote legacy contract and is not made into a hybrid.

The strongest documented threshold-verifiable ballot architecture considered is ElectionGuard. It has guardian quorum key generation, encrypted ballots with validity proofs, homomorphic tallying, verifiable decryption, and public election records. But its maintained SDK/specification is not an EVM verifier contract, does not directly provide this app's anonymous Ethereum eligibility/nullifier integration, and the repository has no audited bridge between its proof system and this chain. This is a candidate for a separately funded integration, not something to improvise in this codebase.

## Per-Option Engineering Conclusions

### A. Commit-reveal

It does not hide the final selection. Publishing a commitment first and revealing later only delays the leak, while associating reveal address/transaction with the commitment can be straightforward. It does not meet permanent ballot secrecy or coercion resistance.

### B. Semaphore-style anonymous eligibility

Semaphore V4 proves membership and knowledge of an identity secret and derives a nullifier from a scope. Its signal/message is public by design. Candidate IDs must never be used as its public signal. Semaphore has no encrypted ballot format, ballot-validity proof for ciphertext, threshold tally, or result protocol; eligibility-only is not private voting.

### C. Semaphore plus encrypted ballot

This is a composition, not a complete established protocol. To be sound it needs a specific, maintained ballot-encryption scheme, proof that each ciphertext encodes exactly one valid candidate, a complete election-specific nullifier domain, authenticated acceptance, threshold decryption or homomorphic tally, and public verification. No compatible complete implementation was found in this repository. We will not assemble these pieces ad hoc.

### D. MACI

MACI is the strongest EVM-native evaluated option and proves that encrypted messages can be processed into publicly verifiable results. However, the documented deployment workflow uses a coordinator MACI private key and the official overview places privacy/collusion resistance under a trusted-coordinator assumption. That violates the explicit no-single-party decryption authority requirement. No maintained threshold/MPC replacement compatible with the required MACI flow was verified; therefore MACI is not selected for this project under the present requirement.

### E. Threshold ElGamal / homomorphic tally

This is a protocol family, not a library selection. A real implementation needs a specified and reviewed DKG, ciphertext encoding, one-hot ballot proofs, anonymous credentials, election-domain nullifiers, aggregation, threshold decryption shares, proofs of correct shares, trustee recovery and independent verification. Writing the missing circuits/contracts or simply collecting decryption shares would be an unverified construction. No-go without a concrete maintained implementation.

### F. ElectionGuard

This is the strongest candidate for the threshold and end-to-end-verifiability requirements: the published process uses guardian-generated keys, a quorum, encrypted ballots with proofs of correct form, homomorphic tallying, verifiable decryption shares, and election-record verification. Missing-guardian recovery is specified through shares distributed during the pre-election ceremony. However, the present project has no supported ElectionGuard-to-EVM proof verifier or anonymous eligibility/nullifier adapter. Hash-anchoring an ElectionGuard election record on-chain would not make the chain validate eligibility or ballot acceptance. Building that bridge here would cross the explicit no-invented-cryptography boundary. Select only after a maintained, reviewed integration is identified and independently audited for this use.

### G. Cicada

Cicada is worth evaluating because it has Solidity code, a Semaphore extension, anonymous nullifiers, ballot-validity proofs and a public finalization proof. It is not acceptable as the production dependency here: upstream explicitly says the contracts are unaudited, has no published releases, uses a default 1024-bit RSA modulus it notes is below normal recommended RSA strength, and provides temporary puzzle-delay tally privacy rather than durable confidentiality of each encrypted ballot. A ballot can be solved individually after the time parameter. These conditions do not meet the project's maintained, mature, defensible protocol threshold.

## Required Key-Management Answer

No key ceremony, trustee roster, threshold, encrypted ballot format, decryption-share verification, failure recovery, trustee replacement, or final tally proof is implemented in this repository. We do not claim a 3-of-5 or any other threshold. For any future ElectionGuard-backed design, those details must come from the selected version's protocol and implementation: independently identified guardians run the documented key ceremony; the configured quorum jointly decrypts only the aggregate; each share is verified; missing guardians are handled only by protocol-supported recovery; compromise and replacement require a new election key/configuration, never unilateral replacement during voting. Do not modify this model based on an unsupported local wrapper.

MACI's documented coordinator private key can decrypt messages, so a single coordinator controlling that key is a single-party privacy risk. No thresholdization is asserted. Cicada's delay assumption is not a threshold key scheme. These fail the explicit requirement as written.

## Eligibility, Nullifier, Domain Separation

No anonymous eligibility proof or election nullifier is implemented. A future integration must bind proof public inputs/domain to at least chain ID, contract address, immutable election ID/version, eligibility root/group, and protocol scope; the election state/time must be enforced by the receiving contract. The public contract must atomically reject used nullifiers. Reusing an identity across groups or deriving stable domains can create cross-election correlation; use the selected protocol's supported identity/group lifecycle rather than inventing a hash construction.

## Transaction and Network Observer Model

Even a sound encrypted-ballot protocol does not hide public EVM transaction metadata: sender, time/block, gas/payment, target contract, calldata bytes, logs and transaction hash. An ordinary observer may correlate wallet → election → ballot submission. If a supported relay is used, the relay sees connection metadata and a submission payload; it may censor or correlate requests unless the protocol and deployment mitigate those risks. Relaying does not hide IP from the relay or provide network anonymity. Wallet, RPC, browser, timing, gas-funding and eligibility issuance remain separate leakage paths. This app has no ballot relay and makes no network-anonymity claim.

## Implementation and Migration Status

- **Implemented:** active frontend voting remains disabled and does not expose the old `castVote` ABI entry; public state/read-only verification remains available for the existing contract.
- **Partially implemented:** existing `#/verify-election` reads the legacy contract directly and checks limited state/tally consistency. It is not a cryptographic private-election verifier.
- **Not implemented:** anonymous eligibility, election nullifier, private ballot, validity proof, threshold tally, protocol-native receipt, private results, decentralized governance, or proof-verification contract.
- **Pending external infrastructure:** a chosen protocol/version with compatible maintained EVM integration, trusted setup/artifacts where applicable, independently governed identity issuance, trustee/coordinator operations, review/audit, RPC/deployment credentials, and real wallet E2E.
- **Decision:** no-go for private voting. Do not create a placeholder privacy contract or claim private/anonymous voting. Existing historical ballots remain public permanently.
