# Production Gap Analysis

**Assessment date:** 2026-09-27  
**Scope:** Existing repository versus the requested privacy-preserving, decentralized academic/testnet target. This is a gap assessment, not a claim that the application is production-ready.

## Severity definitions

- **CRITICAL:** Blocks the stated security/privacy objective or makes deployment unsafe for sensitive elections. Must be resolved or explicitly accepted as out of scope before any controlled-election claim.
- **HIGH:** Could materially undermine election authority, eligibility, state integrity, availability, or user understanding; requires a design and test before testnet/controlled use.
- **MEDIUM:** Important correctness, operations, accessibility, scale, or evidence gap; must be addressed before readiness can be assessed.
- **LOW:** Maintainability or polish gap that is not by itself an election-integrity failure.

The product context matters: direct public votes are not automatically a Solidity coding bug, but they are **Critical** against the requested ballot-secrecy requirement. The current implementation remains suitable only as a visibly public academic demonstration.

## CRITICAL

| ID | Gap | Evidence / impact | Required resolution or explicit decision |
| --- | --- | --- | --- |
| C-01 | Ballot choice is directly linkable to the submitting wallet | `castVote(electionId, candidateId)` calldata and `VoteCast(electionId,candidateId)` disclose choice; sender is public. | Select and integrate a reviewed anonymous voting protocol (membership proof + election-scoped nullifier and a ballot/tally design that does not reveal choice), or declare this system a public poll and remove secrecy claims. Do not invent cryptography. |
| C-02 | No cryptographic separation of real-world eligibility from ballot | Eligibility is `mapping(electionId => mapping(address => bool))`; no ZK group, Merkle membership root/proof, anonymous credential, or nullifier. | Define eligibility issuer, commitment lifecycle, revocation cutoff and proof protocol; independently review the circuit/verifier and contract. Wallet allowlisting alone is not anonymous or Sybil-resistant. |
| C-03 | One owner wallet controls administrative authority | Single OpenZeppelin `Ownable` owner creates elections, sets eligibility, configures candidates, starts/pauses/resumes. A compromised key can control election setup and timing. | Decide governance policy and threshold based on operational membership; integrate a reviewed multisig (e.g. Safe) and optionally a timelock for sensitive operations; test owner/governance handover and emergency controls. |
| C-04 | No controlled-election/privacy readiness boundary is enforced operationally | README warns against real elections, but no deployment gate, verified deployment identity, or policy blocks misconfigured public deployment. | Add an explicit deployment checklist and environment separation; do not label as production/certified. Controlled use requires a protocol, independent audit, observer procedures, identity process, key governance and incident response. |
| C-05 | Active choices/results can be observed before finalization | `getResults` is gated until Finalized, but transaction calldata, event logs and storage are public. Getter gating is not confidentiality. | Do not describe as hidden-result voting. Choose a protocol that cryptographically conceals/tallies votes or remove the hidden-results requirement. Test leakage at transaction/event/storage level. |

## HIGH

| ID | Gap | Evidence / impact | Required resolution or explicit decision |
| --- | --- | --- | --- |
| H-01 | Eligibility authority and issuance are unspecified | Admin manually writes wallet addresses; no voter identity verification, documented issuance rules, review, appeal, or anti-Sybil mechanism. | Specify eligibility governance and evidence, privacy-preserving issuance, duplicate-person handling, appeal and registration cutoff. The identity authority remains an explicit trust assumption. |
| H-02 | Admin pause power and timing policy are underspecified | Owner can pause/resume; pause does not extend `endsAt`, and there is no time bound, required reason, approval threshold, or defined treatment of lost voting time. | Define emergency criteria, public reason/event, authorization threshold, maximum duration/extension policy and voter communication. Test pause boundary and lost-time cases. |
| H-03 | Deployment identity is not verified by frontend | Address is env-configured and checked only for address syntax; no chain-specific allowlist, runtime code check, expected code hash, contract version, source commit or ABI hash validation. | Produce a signed/reviewed deployment manifest and verify chain, code presence/hash, ABI/source/compiler settings and expected version before enabling writes. User-supplied read-only verification must remain possible. |
| H-04 | Single RPC provider with no failover/staleness checks | `getReadClient` creates one client for configured chain/RPC. Read and receipt paths rely on that provider. | Implement bounded multi-provider read fallback or clearly configured user RPC; compare chain IDs and block heights, surface provider identity/staleness, and never retry a write automatically. Define privacy trade-offs. |
| H-05 | No chain reorganization/finality handling | UI waits for a transaction receipt and immediately labels it confirmed. It does not wait a confirmation depth/finality tag or roll back if the inclusion is reorganized. | Define per-network finality policy; model pending, included, confirming, finalized, reorged, timeout, rejected and failed; reconcile on-chain voter/results state after reorg. |
| H-06 | Wallet-control signature is not a replay-protected identity session | Random nonce is locally generated/recovered; there is no consumer, stored nonce, origin/domain field, expiration, or server-side replay state. It proves only current wallet control to local UI code, not election identity. | UI now labels it as wallet-control verification. Keep it as UX only, or use a structured domain-bound challenge (origin, chain, app/contract, nonce, issued/expiry times) with a verifiable nonce-consumption authority. Never use the signature as a substitute for contract caller checks. |
| H-07 | Dormant prototype contains severe insecure features | `legacy/src/db.js` seeds plaintext passwords/DOBs and a hardcoded admin credential; localStorage is editable; `legacy/src/App.jsx` makes role decisions in frontend; `legacy/src/chain.js` is a local simulated ledger with fixed salt/custom fallback hash. | It is now isolated under `legacy/` and is not loaded by active `index.html`; retain an active-entry build guard and never treat it as election truth. |
| H-08 | No independently verifiable election configuration commitment | There is no canonical election/config hash, candidate set commitment, protocol/version commitment, eligibility root or metadata CID validation. Events do not establish a canonical immutable manifest. | Define canonical serialization/version and on-chain commitment before activation; expose a verifier and regression tests for candidate, schedule, metadata and rules. |
| H-09 | Result verification depends on contract-returned totals only | `getResults` returns tally mappings/total after finalization; no independent recount script, event reconciliation, result commitment or proof of completeness exists. | Add reproducible recount from authoritative logs/state, compare against contract counters, verify finalization event/state and surface discrepancies. Document chain archive/RPC assumptions. |
| H-10 | Audit log is incomplete and potentially misleading | Only the last 10,000 blocks are queried; events are not decoded to include actor, timestamp, election ID, or action arguments in the UI; no completeness cursor/contract start block. | Add full bounded/paginated audit with configured deployment block and event decoder; include actor, block timestamp, tx hash, election, status; make truncation/failure explicit and permit independent direct-chain reconstruction. |
| H-11 | No contract/frontend end-to-end or wallet interaction test | Contract tests exist, but no automated browser tests cover wallet connection, network mismatch, message, confirmation, transactions, rejected/failed states, UI role state, or results. | Add isolated local-chain E2E with deterministic wallets and provider; test duplicate/rejected/reverted/reorg behavior and mobile/accessibility. Do not rely on screenshots alone. |
| H-12 | No smart-contract static analysis, fuzzing or invariant testing | Tests cover selected examples but no Slither/Solhint/Foundry fuzz/invariant/formal analysis is configured. | Select tools supported by environment; run and record versions/findings, fuzz state transitions and vote invariants, and retain regression tests. Independent audit still required. |
| H-13 | Single owner can enroll/remove wallets until activation without a review commitment | Eligibility changes are permitted in Draft/Scheduled and emitted with a hashed commitment, while tx input exposes the address. No snapshot process, quorum, published list commitment or appeal exists. | Add transparent eligibility-root publication and multi-party authorization; freeze with an explicit cutoff and audit complete input set off-chain under a documented privacy policy. |
| H-14 | No gas/input bounds for configuration arrays/strings | Candidates and election strings can be added without explicit length/count bounds; reads return whole candidate arrays. At scale this can make reads unusable. | Set protocol-level candidate/string limits or pagination, measure costs, avoid unbounded finalization loops and identify maximum supported academic election size. |
| H-15 | Metadata authenticity and availability are not checked | Metadata URI is arbitrary mutable text; frontend does not fetch/validate CID, digest or schema, nor offer gateway fallback. | Require content-addressed CIDs for immutable election/candidate metadata, commit the canonical CID/hash on-chain, validate schema and document pinning/gateway availability. |
| H-16 | No recovery or key compromise process | One owner key loss compromises administration; no multisig rotation/recovery procedure. A voter wallet loss/change has no protocol. | Define governance-controlled owner recovery and voter identity recovery without silent admin vote reassignment; quantify lost-wallet and compromised-wallet risks. |
| H-17 | No CI, secret scanning, lint or release gate | Package scripts lack `test`, lint, CI, secret scan, dependency/license review, reproducible release artifact or deployment checks. | Add locked, automated CI checks (compile, contract/frontend tests, typecheck, lint, scan, build, accessibility) and protect deployments behind reviewed artifacts. |
| H-18 | Production/testnet environment separation is incomplete | One `.env.local` pattern and two network choices are present; there are no independently managed staging/production manifests or deployment identities. | Define dev/staging/prod manifests and build variables with separate addresses, keys, metadata and RPCs; prevent production secrets from entering Vite builds. |

**Implementation update (2026-09-27):** H-04 is partially mitigated in the active UI: chain-specific read URL lists use viem fallback and contract reads verify the responding chain ID. This does not provide provider quorum, block-hash agreement, source/code verification, or reorganization/finality handling; the gap remains High.

## MEDIUM

| ID | Gap | Evidence / impact | Required resolution or explicit decision |
| --- | --- | --- | --- |
| M-01 | No dynamic network switching from an unsupported network is guaranteed | Supported chain configuration is Hardhat/Sepolia; switch control is only shown when an expected configured chain exists. | Test absent chain, unsupported chain, rejected switch, chain changed during pending write and RPC mismatch. |
| M-02 | Wrong-contract failure handling is generic | Reads fail at call time; no early bytecode/interface/version verification or precise “no contract at address” state. | Validate chain/address/code/version at connection and keep reads disabled on mismatch. |
| M-03 | Transaction state machine omits estimating, awaiting wallet, submitted, confirming, finality and timeout | Current UI uses pending/confirmed/failed/rejected and may not distinguish wallet prompt from receipt wait. | Add explicit state transitions, timeout/replacement tracking and accessible live announcements. |
| M-04 | Input/data validation is incomplete | Address format is checked for eligibility; candidate and election input limits are UI-only, URI is unchecked, contract read arrays are trusted, no malformed response guard. | Validate all boundary data, transaction parameters, lengths, URI scheme/CID and returned state; retain contract validation as authority. |
| M-05 | Admin changes lack explicit per-action review | Ballot has a confirmation modal; administrative actions generally call wallet directly without a summary of network, contract, action, target election and consequence. | Add a common review/transaction-intent screen for critical governance writes. |
| M-06 | No transaction gas estimate or explicit contract summary before signing | UI delegates estimation to wallet/RPC and reports generic errors. | Simulate/estimate where appropriate, show expected action/chain/address/gas warning, then let wallet remain the signer. Never silently resubmit. |
| M-07 | Candidate/result UX exposes counts only after finalization but no independent percentages/verification | No visible config/result commitment, contract code/version, finalization transaction or explorer link for local network. | Add verification page and direct read fields with denominator definitions; clearly distinguish local from public explorer. |
| M-08 | Access control in frontend is presentation-only but menu can obscure admin status | `owner()` determines admin display from current connection; no multisig proposal state. | Keep contract-enforced authorization and show owner, threshold/governance contract and pending proposals if governance is changed. |
| M-09 | Modal accessibility is incomplete | Confirmation markup has dialog role and aria-modal but no focus trap, initial focus, Escape handling, focus restore or tested screen-reader flow. | Implement accessible dialog primitives and automated keyboard/screen-reader-oriented tests. |
| M-10 | Internationalization is not present in the active dApp | Active `App.tsx` strings are hardcoded English; only legacy prototype has translation tables. | Add message-catalog i18n and locale-aware date/time/number rendering. |
| M-11 | Static hosting security headers are not controlled by the repository | Vite output contains no CSP, frame protection, referrer/permissions policy; static host may need host-specific configuration. | Provide compatible headers for supported host and CSP review for injected wallet/RPC/font resources. |
| M-12 | No operational monitoring or incident communication | RPC health, unexpected admin actions, election changes, failures, IPFS health and abnormal activity are not monitored. | Add optional non-authoritative monitoring with privacy disclosure and alert/communications runbook. |
| M-13 | Dependency policy is only partially reproducible | Lockfile exists, but ranges use `latest`; no declared Node/npm pin, license inventory or outdated package review workflow. | Pin supported dependency ranges, declare toolchain version, review licenses and automate updates/audit triage. |
| M-14 | No gas/cost or capacity measurements | Contract writes and deployment are not measured in a versioned report; election/candidate/eligibility operations are assumed to work at demo scale. | Measure deployment/create/candidate/eligibility/vote/end/finalize, chain and compiler settings, and document O(1)/O(n) behavior. |
| M-15 | No content/RPC privacy disclosure beyond ballot choice | RPC operator IP/timing/queries and IPFS gateway request visibility are not described in UI. | Add concise privacy notices and provider configuration/fallback options; avoid calling RPC/IPFS private. |
| M-16 | Read-only verifier is partial, not independent source verification | New view accepts supported chain, address and election ID, verifies chain ID/code presence, and compares finalized candidate sum with reported total. It shares the app's RPC/library and current contract has no commitments. | Add source/runtime hash allowlisting, block-finality awareness, complete log reconstruction and a separate minimal verifier path; do not call current view an audit proof. |
| M-17 | No lost-wallet/voter-change procedure | A wallet replacement cannot be recognized without changing eligibility setup; recovery could be vulnerable to admin identity substitution. | Define whether recovery is unsupported or design a cryptographic re-issuance process with transparent revocation and no silent reassignment. |
| M-18 | No documented chain confirmation policy | Local Hardhat behaves differently from Sepolia; no target-specific confirmation number or finality policy exists. | Document network-specific inclusion/finality assumptions and demonstrate reorg-state handling. |
| M-19 | Accessibility target is not tested | Responsive layout was manually checked, but no WCAG 2.2 AA audit, contrast scan or automated axe test is present. | Perform manual and automated accessibility assessment; record failures and remediation. |
| M-20 | No security operations boundary/recovery runbook | Existing docs omit contract bug response, admin key loss, RPC compromise, chain congestion/reorg, frontend/IPFS failure playbooks. | Write scenario-based operational runbooks and exercise them before controlled use. |

## LOW

| ID | Gap | Evidence / impact | Required resolution or explicit decision |
| --- | --- | --- | --- |
| L-01 | Product surface is narrower than the required site map | Active app has Elections, Administration, Audit log tabs rather than separate voter/public/admin routes and profile/receipt/verification pages. | Decide which pages materially support the demonstration; avoid adding pages that imply unimplemented security. |
| L-02 | Current UI is a single large component | State, data access, voting, administration and audit logic live in `src/dapp/App.tsx`; raises maintenance and testing cost. | Extract tested hooks/components after protocol and state models stabilize. |
| L-03 | Bundle-size warning | Main minified JS is approximately 600 kB and Vite warns above 500 kB. | Lazy-load wallet/admin/audit views and measure compressed transfer and startup. |
| L-04 | Deployment manifest lacks requested provenance fields | Script writes network, chain ID, contract address, deployer, block and ABI; no deployment transaction hash, ABI hash, source commit, compiler config hash, contract version or timestamp. | Extend manifest once release provenance format is agreed. |
| L-05 | README has manual rather than one-command full workflow | Node, deploy, seed and frontend require separate terminals; no automated script starts/tears down an isolated complete E2E environment. | Add a deterministic local orchestration command when test harness is selected. |
| L-06 | Root contains legacy and generated/untracked material | Dormant app and ignored artifacts/manifest can confuse reviewers; the repository currently has active modified/untracked files. | Establish ownership and cleanup policy; never discard user changes during cleanup. |

## Decision gates

1. **Before any public testnet demonstration:** decide ballot secrecy claims, owner governance model, deployment identity verification, testnet key handling, and finality UX.
2. **Before a controlled organization election:** resolve Critical and High gaps, perform an independent contract/protocol audit, define eligibility/recovery/incident procedures, and run full E2E/accessibility/failure tests.
3. **Before any public/legal election claim:** outside the scope of this code review; jurisdiction-specific certification, legal review, operational safeguards, independent election observation and formal assurance remain necessary. Software must not claim governmental-election certification.
