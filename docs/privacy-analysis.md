# Privacy Analysis

**Conclusion:** The active application does not implement privacy-preserving ballots. Voter choice is directly linkable to the caller wallet. This is a public voting demonstration, not a secret-ballot system.

| Data/observer | What can be visible or inferred now | Current mitigation | Residual exposure |
| --- | --- | --- | --- |
| Wallet address | Public transaction sender for each vote/admin call; eligibility address appears in setup calldata. | UI displays shortened address and does not persist a chosen candidate locally after vote. | Wallet is pseudonymous only; address history can identify a person. |
| Candidate selection | `candidateId` appears in `castVote` calldata and `VoteCast` event. | Confirmation warns that choice can be revealed; UI does not show a choice-specific receipt after submission. | Anyone indexing chain can map sender/election/candidate. No ballot secrecy. |
| Transaction metadata | Chain, timing, sender, nonce, gas, input, event, block and transaction hash. | No application backend stores additional transaction metadata. | Publicly correlatable and durable; public mempool may reveal transaction before inclusion. |
| Timing correlation | Voter transaction time and election phase; repeated wallet activity. | None beyond chain protocol. | Observers can correlate participation and external activity. |
| IP address | RPC endpoint may observe client network address, request time and queried contract; public gateways/fonts observe requests. | No private voter data sent as an app API request; browser wallet handles writes. | No Tor/private RPC or traffic protection; users should not assume network anonymity. |
| Eligibility | Wallet allowlist updates and public owner transactions. | Event emits a hashed `(electionId,wallet)` commitment rather than address in the event argument. | Transaction calldata and EVM state are inspectable; hash is not anonymous and small address candidate sets can be tested. |
| Nullifier linkability | No nullifier exists. Duplicate prevention key is wallet address/election. | Per-wallet mapping prevents a second vote from that exact account. | Cross-election addresses are linkable; multiple wallets can represent one person. |
| Administrator | Owner address and all admin transaction senders/actions are public. | Actions emit state/config events; no admin PII fields are stored by active contract. | External attribution can identify administrators and reveal eligibility operations. |
| Metadata | Name and metadata URI strings are public; candidate URIs are emitted in events. | No active content upload mechanism. | Mutable URLs may change; CIDs/gateway requests can reveal user interest; operators might accidentally put personal information in public text. |
| IPFS gateway | If future metadata/UI is loaded through a gateway, gateway observes requests. | IPFS content addressing can verify bytes if CID is checked, but active app does not fetch/validate metadata. | IPFS is public, not private; pinning and gateway availability are external. |
| RPC provider | Query contract, chain and request timing; can observe wallet address if reads are account-specific. | No centralized application API; reads can fail over across configured endpoints and verify reported chain ID. | Each provider observes requests; fallback is not a quorum or privacy relay, and responses are not block-hash reconciled. |
| Coercion/vote selling | Public tx hash plus calldata can serve as proof of selection. | UI does not render a candidate-specific receipt after confirmation. | Chain explorer can still prove the vote; no receipt-freeness/coercion resistance. |
| Real-world identity | Not stored in the active contract. | No names/emails/phone numbers in current contract fields. | Eligibility authority may hold external mapping; address activity or wallet records can identify voters. |

## Design implications

- Solidity `private` prevents autogenerated public getter functions; it does not encrypt storage or hide data from chain observers.
- Hashing predictable/public identifiers does not provide anonymity without a protocol that handles entropy, membership proofs and nullifiers correctly.
- `getResults` reverting before Finalized does not conceal counters or vote calldata from a chain observer.
- A privacy protocol must be designed so proof/nullifier/tally data do not create a trivial link from identity wallet to candidate. Candidate selection cannot remain a plain argument if ballot secrecy is required.
- The safe current statement is: “The contract enforces one ballot per eligible wallet and stores counts on-chain. The wallet, election and candidate selection are public.”
